# Editor loading regression: investigation and repair plan

## What the evidence shows

The September 15 browser trace resolves the immediate failure: `/sdkjs/word/sdk-all.js` returns 404 repeatedly. The response is not JavaScript, so `X-Content-Type-Options: nosniff` correctly blocks it. The converter initialized successfully. `sdk-all-min.js` dynamically requests `sdk-all.js`, but the production build script deleted `sdk-all.js` (and its gzip copy) for word, cell, and slide after Vite copied the runtime. The 404 is the confirmed cause of this session's stuck document, and the same packaging defect can affect spreadsheets and presentations. The build now retains these runtime files and checks the dependency for all three editors. A new deployment is required for the live site to receive them.

The screenshot is the document editor after its shell rendered, with the document placeholder still visible and an upstream warning that components could not load. This warning is a symptom of incomplete editor startup; it does not prove that the network itself is slow.

The September 3 `cb6cb99` fix changed cache headers for stable-path, version-coupled runtime assets and raised RequireJS `waitSeconds` from its seven-second default to 60. The timeout change was made **only** in `public/web-apps/apps/presentationeditor/main/index.html`. The document editor (`index.html` near line 206) and spreadsheet editor (near line 252) still load RequireJS without configuration. This remains a separate cold-start risk, but the new trace shows it was not the immediate cause of this session.

Other failure paths can produce the same indefinite placeholder. `DocumentHandler.vue` waits for the converter script, editor API, and WASM before creating the editor for existing files. It switches its own `loading` state off before `onDocumentReady`; it has no deadline or error transition for `onAppReady`/`onDocumentReady`. Its API script loader also has no deadline. The converter has a 20-second runtime-init timeout, but a failed initialization is only logged by the component and the UI has no recoverable error state. The upstream iframe placeholder can therefore remain after startup or conversion fails.

The LFOS path reads the whole file as an `ArrayBuffer`, wraps it in a `File`, then x2t reads it again into WASM memory. The 55 MB converter bundle is loaded before the editor opens an existing document. This adds cold-start delay and memory pressure. It is an architectural contributor, though there is no evidence that the public file API itself failed in this screenshot.

## Repair sequence

1. Deploy the corrected build and verify that `/sdkjs/{word,cell,slide}/sdk-all.js` returns 200 with a JavaScript MIME type. Then open DOCX, XLSX, and PPTX. Capture stage timestamps: file read, x2t script, WASM ready, conversion, editor API, `onAppReady`, open command, `onDocumentReady`. Preserve the reported trace as a regression fixture: a missing runtime file must fail the build and become a visible UI error if a server still omits it.
2. Make the RequireJS startup policy shared by all three editor entry points, loaded immediately after `require.js`. Use one source or generated fragment, rather than three manually maintained copies. Increase the module deadline based on measured cold-start behavior; do not use an infinite deadline. Add a repository check that all three entry points contain the same policy.
3. Replace the component's implicit loading behavior with explicit states (`reading`, `converter`, `converting`, `editor`, `opening`, `ready`, `failed`). Set `ready` only at `onDocumentReady`. Give every async stage a bounded timeout and a useful error with retry. Ignore late callbacks from a destroyed or superseded editor. A timeout must stop the spinner, not merely log.
4. Preserve one version of the complete editor runtime per page load. Give runtime assets versioned URLs or a release directory, publish atomically, and keep old releases available while existing pages use them. Cache immutable versioned assets; revalidate the entry document and release manifest. Check that nginx and Vercel return the same content types, status codes, and cache policy. Avoid deploying stable paths whose contents change underneath a running page.
5. Start editor shell loading and converter fetch concurrently where safe, then gate document opening on successful conversion and `onAppReady`. Audit the x2t initialization callback/timeout lifecycle and memory use; choose timeout values from actual 55 MB cold-cache measurements. Keep failed conversion distinguishable from failed editor boot.
6. Add realistic browser tests that open DOCX, XLSX, and PPTX in production builds and wait for `onDocumentReady`, including cold cache, slow assets, missing module, failed WASM, and reload across a deployment. Test that each failure becomes a visible retryable error. The existing end-to-end test checks only the launcher, so it cannot catch this regression.

## File API and public documentation

The current `files.read(handle): Promise<ArrayBuffer>` contract forces a whole-file read and copies before conversion. A streaming or chunked read could lower peak memory and let the UI report progress, but it is not required to fix the missing RequireJS policy. If measurements show whole-file transport is a material startup bottleneck, introduce **one canonical** streaming contract and migrate the OnlyOffice app plus every in-scope consumer together. Do not keep an obsolete alias or compatibility shim. Update `LFOS-Documents/docs/capabilities/files.mdx`, `docs/reference/sdk.mdx`, the mirrored AI pages and `llms-full.txt`, and add contract tests asserting the canonical method and rejecting the old name. Check the SDK, LFOS host, and SolOS backend transport as one protocol change. The existing modified documentation files contain unrelated working-tree edits; review and preserve them when making this change.

## Change discipline

Any edit to an editor entry point must be reviewed across document, spreadsheet, and presentation editors. Any change to the bootstrap policy must run the three-editor cold-start test. A release is acceptable only when a failed module or conversion produces a visible error, all three editors reach `onDocumentReady` under the tested slow profile, and a page opened before deployment can still finish against its original runtime version.
